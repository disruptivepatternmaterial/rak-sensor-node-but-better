# Citation registry

Canonical sources for this project. **URLs live here and nowhere else** — code and docs
cite the key (`[CIT-TTN-FUP]`) so a moved link is fixed in one place.

Governed by [`.cursor/rules/20-citation-discipline.mdc`](../.cursor/rules/20-citation-discipline.mdc).
Validated by [`scripts/check_citations.py`](../scripts/check_citations.py), which fails the
build on a reference to an undefined key **and on any entry that is not verified**.

## Verification policy

**Every entry in this registry is verified. An unverified source does not get committed —
it gets verified or left out.** A registry that ships warnings trains people to ignore
warnings, which defeats the point of having a checker.

Verified means the URL was fetched and returned the expected document on the date shown.
Two access quirks are recorded inline rather than treated as a lesser status:

- Some RAKwireless and Nordic pages are JavaScript-rendered, so an automated fetch returns
  only the page title. The URL is confirmed live; open it in a browser for the tables.
- `modbus.org` PDFs reject `HEAD` requests and require a referer. They are confirmed as
  `application/pdf` via a ranged `GET`.

When adding a source: fetch it, confirm it states the fact in the "Establishes" column, and
record the date. Do not add a row from memory.

### Corrections to source *content* — a live URL that is wrong on the facts

The table above is about dead links. This one is worse, because the source is reachable,
authoritative-looking, and wrong — and it was acted on.

**`CIT-RAK-LOWPOWER`, line 45 — "the Serial port MUST NOT be initialized ... FreeRTOS is as well
starting a task running in the background (and never sleeps), that prevents the MCU from
sleeping."**

_Status: **the stated mechanism is false**, and false on RAK's own BSP. Established 2026-08-12 by
reading the core's source. Acted on in `094d5f5` (`FEATURE_CONSOLE=0` in the field image) and
**reverted the same day** — see
[ADR-0008](decisions/ADR-0008-console-in-the-field-image.md), which is now the whole record;
the working review that preceded it has been deleted._

| Claim | What the primary source says | Counter-citation |
|---|---|---|
| Not calling `Serial.begin()` avoids initializing the port | `Adafruit_USBD_Device::begin()` calls `SerialTinyUSB.begin(115200)` **itself** at `Adafruit_USBD_Device.cpp:262`, commented _"Serial is always added by default"_, from `cores/nRF5/main.cpp:52` — **before `setup()`**. A sketch's own call hits `if (isValid()) return;` at `Adafruit_USBD_CDC.cpp:95` and does nothing. | `CIT-TINYUSB`, `CIT-ADA-NRF52-CORE` |
| A background FreeRTOS task is created only if you initialize Serial | The `usbd` task is created at `Adafruit_USBD_Device.cpp:265`, unconditionally, in the same pre-`setup()` path. **RAK's own BSP gets it too:** `-DUSE_TINYUSB` is unconditional at `platform.txt:72` with no `usbstack` menu in `boards.txt`, and RAK's `cores/nRF5/main.cpp` is byte-identical to Adafruit's. RAK's `MAX_SAVE` builds create the task the document warns about. | `CIT-RAK-NRF52-CORE` |
| The task "never sleeps" and prevents the MCU sleeping | `tud_task()` blocks on `xQueueReceive(..., portMAX_DELAY)` (`usbd.c:686`, `osal_freertos.h:81`), so it sits Blocked and off the ready list. SOF interrupts stay disabled for a CDC-only device (`dcd_nrf5x.c:295-302`), so there is no 1 ms wakeup either. | `CIT-TINYUSB-CORE` |
| **Residual claim that survives:** "the hardware of the Serial port consume energy" | True, but it is a **VBUS** question, not a `Serial.begin()` question. `NRF_USBD->ENABLE` is set only from the VBUS power-event handler (`dcd_nrf5x.c:927`), so with no cable the peripheral is never enabled whatever you build. With a cable, `detach()` → `USBPULLUP = 0` (`dcd_nrf5x.c:280`) is the available lever, and `src/power.cpp:135` already uses it. | `CIT-TINYUSB-CORE`, `CIT-NRF-USBD` |

Per [`.cursor/rules/20-citation-discipline.mdc`](../.cursor/rules/20-citation-discipline.mdc):
prior art is not authority, and when prior art and the primary source disagree the primary source
wins and **the disagreement gets written down** — which is what this section is. RAK's document
is narrative prior art *about* code we can read; the code is what runs.

Read charitably, RAK's advice reduces to _do not print_, which is a real duty-cycle-shaped saving
and not the step change the wording implies. **It is not authority for removing the console from a
build**, and the magnitude of any saving remains unmeasured
([#47](https://github.com/disruptivepatternmaterial/rak-sensor-node-but-better/issues/47)).

The lesson generalizes past this row: a vendor doc describing its own product is still
prior art, and `CIT-RAK-LOWPOWER` was strong enough to move a shipping build without anyone
opening the library it describes. Two of the three claims were checkable in minutes.
